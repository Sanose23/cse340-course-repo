TOPIC 1: REGISTRATION AND PASSWORD HASHING

MODEL COACH:
This is project code from src/controllers/users.js. Why is the password hashed before createUser is called?

```js
const { name, email, password } = req.body;
try {
  const passwordHash = await bcrypt.hash(password, 10);
  await createUser(name, email, passwordHash);
} catch (error) {
  if (error.code !== '23505') throw error;
  req.flash('error', 'An account with that email already exists.');
  rememberFormData(req, registrationFields);
  await redirectWithSession(req, res, '/register');
  return;
}
```

SUGGESTED JOSEPH RESPONSE:
The plaintext password should exist only long enough to validate and hash it. The model receives the hash, not the original password, so a database disclosure does not reveal reusable credentials. The duplicate constraint handles concurrent registrations, and the sticky fields exclude password.

MODEL COACH:
Why does the password rule stop at 72 UTF-8 bytes?

SUGGESTED JOSEPH RESPONSE:
bcrypt processes at most 72 bytes, which is not always the same as 72 characters. Enforcing the byte limit avoids accepting two longer passwords that bcrypt would effectively treat as the same prefix.

MODEL COACH:
Why does setup.sql seed roles but not the grader account?

SUGGESTED JOSEPH RESPONSE:
The account must be registered through the application so bcrypt creates its hash. Publishing a reusable hash or plaintext password in setup data would mix test credentials with database structure. The role promotion happens after registration in the intended database.

```js
await regenerateSession(req);
```

SUGGESTED JOSEPH RESPONSE:

TOPIC 3: PROTECTED ACCESS MIDDLEWARE

MODEL COACH:
This is the requireRole factory from src/controllers/users.js. Why is it a factory rather than one ordinary middleware function?

```js
const requireRole = (role) => (req, res, next) => {
  if (!req.session?.user) {
    req.flash('error', 'You must be logged in to access that page.');
    return redirectWithSession(req, res, '/login').catch(next);
  }
  if (req.session.user.role_name !== role) {
    req.flash('error', 'You do not have permission to access that page.');
    return redirectWithSession(req, res, '/dashboard').catch(next);
  }
  return next();
};
```

SUGGESTED JOSEPH RESPONSE:
The outer function captures the role while the route is configured. The returned middleware gets each request and checks the authenticated session against that captured role. The same factory can protect future routes with different roles.

MODEL COACH:
Why must requireRole run before validation middleware on mutation routes?

SUGGESTED JOSEPH RESPONSE:
Authorization should stop an untrusted caller before the application spends time validating or reaches mutation logic. It also prevents validation behavior from leaking details about an admin-only form.

MODEL COACH:
What is the difference between requireLogin and requireRole?

SUGGESTED JOSEPH RESPONSE:
requireLogin verifies that a session has an authenticated identity. requireRole adds authorization by requiring that identity to hold a particular role. Authentication answers who the user is; authorization answers what that user may do.
